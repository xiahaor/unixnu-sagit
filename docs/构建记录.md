### 失败 1：BaseTools 编不过（C23 语义）

```
main.c:163: error: too many arguments to function 'p->process'; expected 0, have 2
globals.c:204: error: initialization of 'struct _tree * (*)(void)' from incompatible pointer type ...
```

根因：GCC 15 默认 `-std=gnu23`（C23 里 `f()` 表示零参数），而 `Pccts`（antlr/dlg）是 K&R 时代代码。
另：这两个 makefile 是 **CRLF** 行尾，`sed 's/^COPT=-O$/'` 匹配不到（`COPT=-O^M$`）。

修复（本地改动）：把 `COPT=-O` 改为 `COPT=-O -std=gnu89`
- `BaseTools/Source/C/VfrCompile/Pccts/antlr/makefile:172`
- `BaseTools/Source/C/VfrCompile/Pccts/dlg/makefile:122`

### 失败 2：BrotliCompress 缺子模块

```
BrotliCompress.c:20: fatal error: ./brotli/c/common/constants.h: 没有那个文件或目录
```

修复：`git -C Common/edk2 submodule update --init --depth 1 BaseTools/Source/C/BrotliCompress/brotli`
（子模块 commit `f4153a09f87cbb9c826d8fc12c74642bb2d879ea`）。

### 失败 4：固件 overlay 要求 Mu 检出里有 libfdt

```
error: missing in Mu checkout: MdePkg/Library/BaseFdtLib/libfdt/libfdt/libfdt.h
```

而 GitHub 直连当时超时（`curl 28 ... port 443`）。

（该版本里 `libfdt` 是目录不是 gitlink，`libfdt/libfdt.h` 随 tarball 一起下来；
overlay 只检查路径存在，见 `unixnu-sagit/tools/apply-edk2-unixnu-overlay.sh:64-67`。）

### 失败 5：overlay 里 `mkdir: Permission denied`

根因：`apply-edk2-unixnu-overlay.sh:112` 里 `TMPDIR="${TMPDIR:-/data/opencode/tmp}"`，本机没有 `/data`。

修复：构建时显式传 `TMPDIR=/home/xiahaoran/dsh/unixnu/tmp`（已提前建好该目录）。
`tools/build-xnu-sagit.sh:25` 也是同样的默认值，编内核时同样要传。


### 失败 6：overlay 的 DSC 锚点不存在

```
.../sagit.dsc: RamDiskDxe anchor not found
```

根因：overlay 的 `anchor2` 要求设备 DSC 里已经有 `  SagitPkg/Drivers/RamDiskDxe/RamDiskDxe.inf`
（`apply-edk2-unixnu-overlay.sh:276-278`），但 `edk2-msm8998` 的 `sagit.dsc` 只有 22 行、靠 `!include Msm8998.dsc`，
本身没有 `[Components]` 段，也没有这一行。

处理：在 `sagit.dsc` 末尾显式追加 `[LibraryClasses.common]`/`[Components.common]` 段
（UniXNULib、UniXNUDxe、Sagit RamDiskDxe、Sagit ReportDxe、UniXNU 应用含 FdtLib 指向 MdePkg/BaseFdtLib、DarwinBoot），
这样 overlay 检测到 `UniXNUPkg/Driver/UniXNUDxe` 已存在就会跳过 DSC 追加，只做 FDF 的插入
（FDF 锚点 `# INF src/kernelfdt/KernelFdtDxe.inf` 在 `sagit.fdf:245` 确实存在）。
原文件备份在 `/tmp/sagit.dsc.orig`。

### 失败 7：SimpleInit rootfs 需要 `msgfmt`

```
== SimpleInit rootfs ==
```

处理（**免 root**）：`apt-get download gettext` 后 `dpkg-deb -x` 解到 `toolchains/apt-root/`，

```sh

P=/home/xiahaoran/dsh/unixnu/toolchains/apt-root
for d in /tmp/debs/*.deb; do dpkg-deb -x "$d" "$P"; done
export PATH="$P/usr/bin:$PATH"
export LD_LIBRARY_PATH="$P/usr/lib/x86_64-linux-gnu"
```


### 失败 8：子模块"有目录但工作树是空的"

EDK2 `build` 连续报三类同样的错：

```
GPLDrivers/Library/simple-init/SimpleInit.dec(13): File/directory not found: libs/freetype/include
MdeModulePkg/MdeModulePkg.dec(29): File/directory not found: Library/BrotliCustomDecompressLib/brotli/c/include
CryptoPkg/CryptoPkg.dec(25): File/directory not found: Library/OpensslLib/openssl/include
```

根因：`git submodule update --init` 虽然把目录建出来，但**工作树是空的**（只有 `.git` 文件）。
这是设备仓库 `docs/EDK2-BUILD.md:29-46` 早就记录过的坑（"Check for the actual files, not the status line"）。

处理：
1. `simple-init` 的 `libs/freetype`：`git submodule update --init --depth 1 libs/freetype`（GitLab）。
2. edk2 的 brotli / openssl / berkeley-softfloat-3 / cmocka 等：在各自目录里 `git reset --hard HEAD && git checkout -f`。
3. 批量检测命令（可复用）：
   ```sh
   cd edk2-msm8998/Common/edk2
   for p in $(git config -f .gitmodules --get-regexp 'submodule\..*\.path' | awk '{print $2}'); do
     [ "$(ls -A "$p" 2>/dev/null | wc -l)" -le 1 ] && echo "EMPTY: $p"
   done
   ```

## ✅ 2026-11-13 18:39 · IPSW 与 kernelcache 核对通过

用户开放 root 后继续。IPSW 取自 ipsw.me 的 iPhone 8（iPhone10,1）16.7.16 / 20H392：

```
ipsw/iPhone_4.7_P3_16.7.16_20H392_Restore.ipsw   6,035,280,776 B
  内核缓存成员 kernelcache.release.iphone10      18,213,846 B（IM4P 外层是 DER 封装，不是裸 IM4P）
  DeviceTree: Firmware/all_flash/DeviceTree.d20ap.im4p
```

解包链路（DER → OCTET STRING → LZFSE → fat Mach-O → 取 arm64 切片）：

1. DER 结构：`SEQUENCE { IA5String "IM4P", IA5String "krnl", IA5String "KernelCacheBuilder_release-2429.140.2", OCTET STRING(18,211,212) }`
2. OCTET STRING 的内容就是 **LZFSE 流**（以 `bvx2` 开头），从文件偏移 **62** 开始。
3. 用自建 `lzfse`（`lzfse` 官方源码 `make`，`/tmp/lztest/build/bin/lzfse`）解出 **51,019,804 B** 的 fat Mach-O
   （magic `0xbebafeca`，内含 1 个 arch：cputype `0x0100000c` = arm64）。
4. 取出 arm64 切片（51,019,776 B）：

```
sha256 ae36144edbd1aebce562b662ed0c19053c95026d0950eeab5c9e695fe72e2f71
```

**与 OS profile 的 pin 完全一致**（`unixnu-sagit/profiles/os/ios-16.7.16-20H392/profile.toml:31`）⇒ 下载的 IPSW 型号/版本正确，
kernelcache 已就位：`ipsw/kernelcache.arm64`。

> 注意：BuildManifest 里的 `KernelCache.Digest`（`e3da058c…`）不是这个切片的哈希，
> 不能拿来当校验依据；profile 的 pin 是**切片后**的 sha256。

### 失败点定位（不是猜，是挖字符串）

打印串来自内核镜像本身（`strings out/kernel.stripped.macho`）：

```
failed to read boot nonce hash: secure boot level = %#llx: %d
```

对应 AppleImage4 的 nonce manager 去读 NVRAM 项 `com.apple.System.boot-nonce`
（XNU 侧 `iokit/Kernel/IONVRAM.cpp:217` 有该键的定义），而我们只有 EDK2/UniXNU 的 NVRAM 代理，
没有 iBoot 写入的 nonce ⇒ 返回 2（ENOENT）。设备仓库文档把这一项列为"未解决边界"，
并明确他们的 bring-up 顺序是**先关安全组件、后补 PMGR/AMFI**（`docs/FOREIGN-PORT-GAP.md:456`）。

## ✅ 2026-11-14 13:4x · 越过 AppleImage4，内核进入 BSD/kext 阶段（v4/v5）

### 依赖链（从 kernelcache 的 PRELINK_INFO 实测，不是猜）

```
com.apple.security.AppleImage4  ← com.apple.filesystems.apfs
                                ← com.apple.driver.AppleMobileFileIntegrity (AMFI)
com.apple.kext.CoreTrust        ← AppleImage4 / AMFI
AMFI                            ← com.apple.iokit.IOHIDFamily
```

v2（只照 roots 删）失败：闭包把 CoreTrust/AppleImage4 拉回来了 → 证明工具按 `OSBundleLibraries` 传递闭包。
v3（再删 apfs）仍带 Image4：因为 **IOHIDFamily → AMFI → Image4** 这条链还在。
v4（同时删 apfs 与 IOHIDFamily）：闭包 10 个组件，**无 AppleImage4 / CoreTrust / AMFI** → 真机越过 nonce panic。

### 2026-11-14 15:3x · 找到 arm64 下第三方块驱动的合法接法（关键机制）

`-Wl,-undefined,dynamic_lookup` 这条路走不通：cctools-port 的 ld64 在 arm64 上直接断言

**源码编入的类**（`libSourceStorage.a`），内核里同时还合并了**预链接的原版 IOStorageFamily kext**；
两者的 `gMetaClass` 地址必然不同 ⇒ 上机会直接 panic 在 bsd_init 之前，什么都看不到。

因此把注册函数改成**诊断模式**（`NativeUfs.cpp:842-852`）：
- `OSKextLoadKextWithIdentifier` 失败 / ABI 不匹配时 **只 IOLog 具体地址与 class size，然后 return**，
  不再 panic、也不再做 `preModLoad/postModLoad`；
- 这样本次上机至少能确定：① 源存储类是否让内核照常走到 kext 阶段 ② 原存储 kext 能否被加载
  ③ 两边类的实际地址/大小（打出来就能判断下一步走"源码类"还是"绑原版类"）。

### 2026-11-14 15:2x · 驱动力注册机制读清楚了（v9 可能真的会碰到 UFS）

`OSMetaClass::preModLoad(kextIdentifier)` 并不"扫描某个 kext 的类"，它只是把全局状态 `sStalled`
准备好并上锁（`libkern/c++/OSMetaClass.cpp:503-545`）；**真正把类塞进 sStalled 的是类的 OSMetaClass
构造函数**（即 `OSDefineMetaClassAndStructors` 里那段，在 C++ 静态初始化函数
`__GLOBAL__sub_I_<file>.cpp` 里执行）。`postModLoad` 再把 sStalled 里的类批量注册进 sAllClassesDict。

由此：
- 驱动末尾的 `p11_ufs_static_init()` 就是显式调用 `__GLOBAL__sub_I_NativeUfs.cpp`，
  让 `NativeUfs` / `NativeUfsLun` 的元类构造在"停牌"期间发生，随后一次 `postModLoad` 批量注册；
- 我们的**源码存储类**（`libSourceStorage.a`）如果其静态初始化函数在内核早期被执行过，
  那么 `IOBlockStorageDevice` 等类**已经注册**，此时 `getMetaClassWithName` 返回的就是源码类、
  与 `&IOBlockStorageDevice::gMetaClass` 相等 ⇒ v9 的 ABI 校验会**通过**，驱动会真的走到
  `preModLoad/postModLoad` 注册、匹配 `/arm-io/ufshc`、碰 UFS 硬件；
- 反之（静态初始化没执行/被丢弃）就只会打印 mismatch 并安全返回。

所以 v9 的结果有信息量：要么看到 `P11 UFS: ... registered ...` 之后进入硬件读取，要么看到
mismatch 行（顺便带出原版类地址/大小）。无论哪种都能定下一步。


### 2026-11-14 15:3x · 源码存储类带静态初始化（v9 有望真的走到 UFS）
